# 英文法规知识图谱数据转英文知识条目规则设计

> 依据：英文法规格式一、格式二和格式三原始材料，`en_law_v1`、`en_law_v2`、`en_law_v3` 三套本体 Schema，以及当前英文法规 Neo4j 导出数据。
>
> 核心原则：**知识正文使用英文、法规原文优先、多层完整正文均可产出、结构字段只作元数据、关系必须可核验、完全相同的机械重复只保留一份**。

---

## 0. Source-context rule

1. Knowledge whose semantic subject is a `LegalDocument` remains document-level prose and does not receive an `Under` prefix.
2. Knowledge generated from legal provisions, clauses, paragraphs, items, amendments, legal-text citations, and other non-document subjects uses `Under {document name}, {knowledge body}`.
3. The converter associates nodes with their document through `filename` and prefers the canonical `LegalDocument` name. If the document node is missing, it falls back to the path-free and extension-free filename.
4. Source context is added at the centralized entry-construction boundary. Existing rule templates must not add a second `Under` prefix.
5. Prefixing changes rendered English content only; deduplication text, entry count, source metadata, hierarchy filtering, and public converter interfaces remain unchanged.

## 1. 数据特点与设计目标

### 1.1 三类英文法规资料

当前英文法规材料主要包含三种结构形式：

| 格式 | 典型资料 | 主要结构标识 | 对应 Schema |
| --- | --- | --- | --- |
| 格式一 | 欧盟 Regulation、Directive 等 | `Article`、Chapter、Section、Annex | `en_law_v1` |
| 格式二 | 美国 Act、Public Law 等 | `SEC.`、`SECTION`、Title、Part、subsection | `en_law_v2` |
| 格式三 | U.S. Code、CFR、ITAR 等 | `§`、Part、subsection、paragraph | `en_law_v3` |

三类材料在章节标识、编号方式和正文组织上存在差异。格式一常在正式条文前包含较长的立法理由；格式二常包含对既有法律的插入、替换、删除和修订文本；格式三除现行条文外，还可能混有编辑说明、修订沿革和法定注释。因此，知识条目转化不能仅依赖 Markdown 标题或文件版式，而应以图谱中的业务实体类型、层级关系、来源正文和定位编号为依据。

三套 Schema 的核心语义模型已经基本一致，可统一归一为：

```text
LegalDocument
  ├─ BASED_ON → LegalBasis
  └─ CONTAINS → LegalProvision
                    └─ CONTAINS → ProvisionClause
                                         └─ CONTAINS → ProvisionTextParagraph
                                                              ├─ CONTAINS → ProvisionTextParagraph
                                                              └─ CITES → Citation
```

其中，三种格式保留各自原始法律定位符，不把 `Article 1(1)`、`SEC. 101(a)` 和 `§ 3729(a)(1)`强行改写为同一种编号形式。

### 1.2 当前图谱情况

当前 Neo4j 导出数据包含以下业务对象：

| 业务类型 | 数量 | 主要用途 |
| --- | ---: | --- |
| `LegalDocument` | 39 | 法规文件身份、发布日期、目的和适用范围 |
| `LegalBasis` | 41 | 法规文件的明确制定或授权依据 |
| `LegalProvision` | 3,041 | `Article`、`SEC.` 或 `§` 级法条及其定位上下文 |
| `ProvisionClause` | 12,422 | 法条下的 subsection、paragraph 或其他条款单元 |
| `ProvisionTextParagraph` | 20,454 | 当前图谱中最细粒度的法规原文单元 |
| `Citation` | 3,702 | 正文中明确出现的法规、法条或法律工具引用 |

现有图谱覆盖格式一25份文件、格式二14份文件。格式三已有原始材料和 Schema，但当前导出数据中尚无对应图谱样本。因此，格式三采用与前两类相同的统一规则，同时保留 `§` 定位方式；其具体示例标注为基于原文和 Schema 的规则示例，不作为当前图谱实证结果。

图谱转化还需处理以下实际情况：

1. 部分父子节点保存了完全相同的正文，不能按节点数量直接逐个输出。
2. 部分 `ProvisionClause` 没有有效正文子节点，但其自身保存了完整条款原文，仍可独立形成条款级知识。
3. `LegalProvision`、`ProvisionClause` 和 `ProvisionTextParagraph` 分别表达法条、条款和细分正文层级。父级正文即使包含子级内容，也可能保留共同前提、完整语境或整体规范结构，因此不能仅因存在子节点就默认删除。
4. 内部引用可能只识别出引用文本，尚未解析到同一图谱中的目标节点。
5. 历史抽取结果包含少量 Schema 外动态属性，不应被转化为知识正文。
6. Neo4j 无法直接保存字典对象，量化条件通常以 JSON 字符串形式存储，转化时需要恢复为结构化对象。

### 1.3 设计目标

本规则需要实现以下目标：

1. 将三种英文法规图谱统一转化为正文为英文的知识条目。
2. 优先保留可回到原始法规核验的完整原文，不使用摘要替代已有正文。
3. 为知识正文补充法规名称和条文位置，使其能够脱离图谱上下文独立理解。
4. 允许法条、条款和正文段落形成不同粒度的知识，保留有助于完整理解的跨层语义重叠，仅删除标准化后正文完全相同的机械重复。
5. 将规范功能、主体、行为、条件、后果、行业和风险类型等字段作为检索元数据，不重复拼装事实不完整的新句子。
6. 保留有效量化条件、修订属性、制定依据和引用关系，并避免臆造未解析目标。
7. 在 TXT 中只输出英文知识正文，在 JSON 或 JSONL 中保留来源、定位、分类和校验信息。

## 2. 英文法规知识的判定标准

### 2.1 什么可以作为知识条目

英文法规知识条目应当是能够回答一个明确问题，并能够回到法规文件或图谱关系进行核验的英文命题或法规原文片段。主要包括：

1. **文件身份事实**：文件名称、编号、性质和发布主体构成的完整身份信息。
2. **发布与效力事实**：明确的发布日期、生效日期或适用日期。
3. **主题、目的和范围事实**：文件明确说明的监管主题、制定目的和适用范围。
4. **规范正文知识**：定义、义务、禁止、许可、条件、例外、法律后果等可独立理解的法规正文。
5. **修订知识**：明确规定插入、替换、删除、修订或废止其他法律内容的条文。
6. **制定依据知识**：法规文件通过有效关系指向明确法律依据。
7. **外部引用知识**：某一正文单元通过有效关系明确引用可核验的外部法规、法条或法律工具。

### 2.2 什么不单独作为知识条目

以下内容不因其在图谱中有字段或节点就自动形成独立知识：

1. 图谱标签、节点 ID、关系 ID、批次标识和内部文件路径。
2. `CONTAINS` 表达的文件、法条和条款组织关系。
3. `core_topic`、`clause_summary` 等摘要或检索标题。
4. 合规域、经济行业、适用行业和合规风险类型等分类标签。
5. `mandatory`、`prohibition`、`optional` 等规范功能分类本身。
6. 主体、行为、条件、后果和例外等已被完整原文覆盖的结构化字段。
7. 没有有效关系来源的孤立 `LegalBasis` 或 `Citation` 节点。
8. 无法证明属于现行规范正文的目录、页码、编辑说明或孤立标题。
9. 量化特征和量化条件本身。正文中的数值内容随完整法规原文输出，结构化量化对象只作为元数据，不另行生成量化知识。
10. 无效量化对象及其降级处理结果。解析失败只记录校验问题，不形成自然语言知识。
11. 内部引用或未解析引用。引用原文仍保留在法规正文中，引用文本和解析状态可作为结构化信息保存，但不另行生成引用知识。

### 2.3 原文优先原则

当图谱已经保存完整法规原文时，不再根据主体、行为、条件和后果字段重新拼装第二条规则知识。结构化字段用于分类、筛选、规则计算和质量审核，法规原文用于知识正文。这样可以避免结构化字段缺失或组合顺序错误造成法律语义变化。

知识正文的基本模板为：

```text
Under {document_display_name}, {source_locator} provides: {source_text}
```

如果原文已经包含完整定位，或者使用 `provides:` 会造成明显语法不顺，可使用：

```text
{document_display_name}, {source_locator}: {source_text}
```

模板只补充来源上下文，不改写法规原文中的主体、情态、条件、例外、数字或法律后果。

## 3. 知识产出类型

| knowledge_type | 中文说明 | 来源 | 产出条件 |
| --- | --- | --- | --- |
| `document_identity` | 文件身份知识 | `LegalDocument` | 文件名称有效，并至少有编号、类型或发布主体之一 |
| `document_effect` | 发布与效力知识 | `LegalDocument` | 发布日期、生效日期或明确适用日期至少一个非空 |
| `document_subject_purpose` | 主题与目的知识 | `LegalDocument` | 主题或目的至少一个非空 |
| `document_scope` | 适用范围知识 | `LegalDocument` | 适用范围明确且能够独立表达 |
| `legal_basis` | 制定依据知识 | `BASED_ON` | 来源文件、目标依据和关系均有效 |
| `legal_provision` | 一般法规正文知识 | `LegalProvision`、`ProvisionClause`、`ProvisionTextParagraph` | 存在有意义的英文原文；不同层级可分别产出，正文完全相同时去重 |
| `amendment_provision` | 修订法规正文知识 | 法条或正文实体 | 原文明示修订、插入、替换、删除或废止行为 |
| `citation` | 外部引用知识 | `CITES` | 来源正文、外部引用目标和关系均有效，且目标已经明确解析 |

`knowledge_type` 使用英文受控值。合规风险类型等中文受控分类可以保留在元数据中，但不得写入英文知识正文。

## 4. 总体转化流程

### 4.1 Neo4j 导出结构解析

节点文件按以下结构解析：

```text
item["n"]["identity"]
item["n"]["labels"]
item["n"]["properties"]
```

关系文件按以下结构解析：

```text
item["p"]["identity"]
item["p"]["start"]
item["p"]["end"]
item["p"]["type"]
item["p"]["properties"]
```

节点的业务类型必须读取 `n.properties.label`。`n.labels` 是 Neo4j 图谱标签或导出批次标签，不能作为知识类型。关系端点必须通过节点 `identity` 与关系 `start`、`end` 建立索引，不应使用节点名称匹配，因为同一文件中可能存在大量同名或同编号显示值。

### 4.2 格式归一化

三种格式统一映射到相同的业务实体和知识类型，但保留原始定位方式：

| 原始格式 | 法条定位示例 | 条款定位示例 | 转化要求 |
| --- | --- | --- | --- |
| 格式一 | `Article 1` | `Article 1(1)(a)` | 原样保留 `Article` 编号 |
| 格式二 | `SEC. 101` | `SEC. 101(a)(1)` | 原样保留 `SEC.` 或 `SECTION` 编号 |
| 格式三 | `§ 3729` | `§ 3729(a)(1)(A)` | 原样保留 `§` 及多级定位 |

定位符只用于来源说明和去重，不转换为中文，也不强制改成统一编号样式。

### 4.3 构建上下文索引

转化前应一次性构建：

1. 节点 `identity` 到节点对象的索引。
2. 每个节点的出边和入边索引。
3. 文件到法条、法条到条款、条款到正文单元的层级索引。
4. 正文单元到引用节点的关系索引。
5. 节点到所属文件和完整法律定位路径的反向索引。

这些索引用于恢复知识上下文、识别父子正文是否完全相同、解析关系端点和保留来源信息，不用于生成“包含”类知识句。

### 4.4 候选生成与质量处理

总体顺序为：

```text
解析节点和关系
  → 识别业务类型与文件格式
  → 恢复所属文件和法律定位
  → 分别生成法条级、条款级和最小正文单元候选
  → 生成文件事实、制定依据和引用知识
  → 校验英文、量化对象、关系端点和属性白名单
  → 删除正文完全相同的跨层机械重复
  → 输出 TXT 与 JSON/JSONL
```

## 5. 实体属性处理规则

### 5.1 `LegalDocument`

`LegalDocument` 只生成少量分组后的文件事实，不逐属性拆分。

| 属性 | 处理方式 | 说明 |
| --- | --- | --- |
| `document_name` | 组装文件知识 | 文件显示名称的首选值 |
| `short_title` | 显示名兜底或别名元数据 | 仅当不为空且不与全称重复时使用 |
| `document_number` | 组装身份知识 | 与名称、类型和发布主体组合 |
| `document_type` | 组装身份知识 | 如 Regulation、Directive、Act |
| `issuing_authority` | 组装身份知识 | 仅使用原图谱明确值 |
| `publication_date` | 组装发布效力知识 | 不自行推算日期 |
| `effective_date` | 组装发布效力知识 | 不自行推算日期 |
| `subject_matter` | 组装主题目的知识 | 与目的重复时去重 |
| `purpose` | 组装主题目的知识 | 保留明确目的，不从风险标签反推 |
| `scope_of_application` | 组装范围知识 | 为空或不能独立表达时跳过 |
| `legal_basis_text` | 校验或兜底提示 | 有效 `BASED_ON` 关系优先；不直接按该字段生成依据知识 |
| `document_format` | 元数据 | 用于格式路由 |
| `compliance_domains`、`economic_industries`、`applicable_industry`、`risk_types`、`合规风险类型` | 元数据 | 不进入英文正文 |
| `filename`、`source_filename` | 来源信息 | 不单独生成知识 |
| `name`、`label`、`id`、`graph_level`、`graph_tag` | 控制或内部字段 | 不进入正文 |

文件显示名按以下优先级确定：

```text
document_name
  > 非泛化 short_title
  > source_filename 或 filename 的文件名主体
```

`An Act` 等泛化名称不能覆盖更有辨识度的简称或文件名。

建议模板：

```text
{document_name} ({document_number}) is a {document_type} issued by {issuing_authority}.
{document_name} was published on {publication_date} and took effect on {effective_date}.
{document_name} concerns {subject_matter} and aims to {purpose}.
{document_name} applies to {scope_of_application}.
```

空字段不进入句子；主题与目的表达相同时只保留一次。

### 5.2 `LegalBasis`

`LegalBasis` 是关系目标，不按节点属性独立输出。只有当存在有效的：

```text
LegalDocument - BASED_ON → LegalBasis
```

关系时，才生成 `legal_basis` 知识。

依据显示文本按以下优先级确定：

```text
citation_text
  > official_title
  > instrument + article
  > name
```

模板：

```text
{document_display_name} is based on {basis_display_text}.
```

孤立依据节点、目标文本为空或关系端点无效时不产出。

### 5.3 `LegalProvision`

`LegalProvision` 对应格式一的 `Article`、格式二的 `SEC.` 或格式三的 `§`。除提供法条定位、章节上下文和修订信息外，其完整法条正文也可以形成法条级自然语言知识，用于保留同一法条内各条款的共同前提和整体语境。

| 属性 | 处理方式 | 说明 |
| --- | --- | --- |
| `provision_number` | 定位字段 | 作为 `source_locator` 的法条级部分 |
| `provision_heading` | 标题元数据 | 可用于检索，不单独生成标题知识 |
| `provision_content` | 法条级知识正文 | 原文有效时生成法条级候选；与后代正文完全相同时去重 |
| `core_topic` | 元数据 | 摘要不能替代正文 |
| `scope_of_effect` | 元数据 | 已有正文时不另行组装范围句 |
| `is_amendment_article` | 类型判定 | 与原文和修订字段共同判定修订知识 |
| `amendment_action`、`amendment_target` | 修订元数据 | 不脱离完整原文单独造句 |
| `title`、`chapter`、`part`、`section` | 来源路径 | 用于定位和审计 |
| 行业、合规域等分类字段 | 元数据 | 不进入正文 |
| 内部控制字段 | 过滤 | 不进入正文 |

法条存在有效条款或正文后代时，不应因此直接丢弃 `provision_content`。如果法条全文汇总了多个条款、包含共同前提或提供完整法律语境，应保留法条级知识；如果标准化后的法条全文与某一个后代正文完全相同，则只保留一条。法条全文只是由多个子级正文组合而成时，仍允许与子级知识同时存在，因为二者分别服务整体理解和精确检索。

### 5.4 `ProvisionClause`

`ProvisionClause` 是代码切分形成的 subsection、paragraph 或其他可引用条款单元，位于法条和最细正文之间。

| 属性 | 处理方式 | 说明 |
| --- | --- | --- |
| `unit_number` | 定位字段 | 与法条编号组合形成完整位置 |
| `unit_content` | 条款级知识正文 | 原文有效时生成条款级候选；与子级正文完全相同时去重 |
| `unit_level` | 元数据 | 记录结构层级 |
| `clause_summary`、`clause_purpose` | 元数据 | 不替代原文，不单独输出 |
| 主体、行为、条件、后果、例外等结构字段 | 元数据 | 不拼装第二条规则知识 |
| `legal_function` | 元数据 | 受控值用于筛选和审核 |
| 分类字段 | 元数据 | 不进入正文 |
| 内部控制字段 | 过滤 | 不进入正文 |

存在正文子节点时，条款正文仍可独立产出，以保留条款的共同条件、完整列举和整体上下文。若标准化后的条款正文与某一个正文子节点完全相同，则只保留一条；若条款正文包含多个子节点内容，或者与子节点存在部分语义重叠但并不完全相同，则条款级知识和子级知识均予保留。条款没有有效子节点时，只要 `unit_content` 有效，同样正常生成条款级知识，而不是将其视为特殊兜底结果。

`clause_summary` 不能在 `unit_content` 缺失时自动替代正文，因为摘要可能省略条件、例外或法律后果。

### 5.5 `ProvisionTextParagraph`

`ProvisionTextParagraph` 是首选知识正文来源。

| 属性 | 处理方式 | 说明 |
| --- | --- | --- |
| `unit_number` | 定位字段 | 必须保留原始 `Article`、`SEC.` 或 `§` 路径 |
| `unit_content` | 核心知识正文 | 使用原文，不翻译、不摘要、不补写 |
| `quantitative_feature` | 类型与校验元数据 | 与量化对象联动校验 |
| `quantitative_indicator` | 结构化元数据 | JSON 字符串解析后保存 |
| `legal_function` | 元数据 | 不生成分类句 |
| 主体、行为、角色、条件、后果、例外、时间和目的 | 元数据 | 用于筛选、解释和校验，不重复拼装正文 |
| 分类字段 | 元数据 | 不进入英文正文 |
| Schema 外动态属性 | 过滤并统计 | 不作为知识来源 |
| 内部控制字段 | 过滤 | 不进入正文 |

`unit_content` 必须满足：

1. 非空且不是孤立编号或标题。
2. 能够回到当前条款和文件。
3. 以英文为主，不包含异常混入的中文说明正文。
4. 不与同一路径下已保留的更细粒度正文重复。

满足条件后，使用文件名称和 `unit_number` 补充上下文，正文内容保持原样。

### 5.6 `Citation`

`Citation` 是引用关系目标，不按节点列表全量输出。只有存在有效的外部引用关系，并且引用目标已经明确解析时，才考虑生成 `citation` 知识：

```text
ProvisionTextParagraph - CITES → Citation
```

关系时，才考虑生成 `citation` 知识。

引用显示文本按以下优先级确定：

```text
citation_text
  > official_title + provision_number
  > official_title
  > name
```

`citation_purpose` 明确且不会重复正文时，可以追加到句尾。内部引用和未解析引用不生成独立自然语言知识；其原始引用文本已经包含在法规正文中，必要的引用文本与解析状态仅保留为结构化信息。

## 6. 关系处理规则

| 关系 | 合法端点 | 是否产出知识 | 处理方式 |
| --- | --- | --- | --- |
| `CONTAINS` | 文件→法条、法条→条款、条款→正文、正文→正文 | 否 | 恢复上下文、来源路径和正文层级，并辅助识别完全重复 |
| `BASED_ON` | `LegalDocument`→`LegalBasis` | 是 | 生成一条英文制定依据知识 |
| `CITES` | `ProvisionTextParagraph`→`Citation` | 条件产出 | 仅在来源有效、目标为外部引用且已经明确解析时生成英文引用知识 |

### 6.1 `CONTAINS`

`CONTAINS` 是组织关系。它用于确定某正文属于哪一条法条、哪一份文件，并辅助比较同一祖先链中的父子正文是否完全相同。它不用于判断父级知识是否因包含子级内容而被删除，也不得生成以下低价值句子：

```text
Regulation (EU) 2023/956 contains Article 1.
Article 1 contains Article 1(1).
```

### 6.2 `BASED_ON`

只有来源文件、目标依据和端点类型均有效时产出。多个依据节点分别表达不同依据时，可每条关系生成一条；完全相同的依据文本应去重。

模板：

```text
{document_display_name} is based on {basis_display_text}.
```

### 6.3 `CITES`

模板：

```text
Under {document_display_name}, {source_locator} cites {citation_display_text}.
Under {document_display_name}, {source_locator} cites {citation_display_text} {purpose_suffix}.
```

引用知识必须满足：

1. 来源节点能够解析到所属文件和正文位置。
2. `CITES` 关系端点存在且类型合法。
3. 引用文本能够明确识别。
4. 引用目标属于外部法规、法条或法律工具，并且已经明确解析。
5. 不根据简称或编号猜测外部实体 ID。
6. 内部引用和未解析引用不生成引用知识，只保留原始引用文本和解析状态。

## 7. 多层正文产出与重复控制

### 7.1 多层正文产出原则

正文知识按照图谱中的三个结构层级分别生成候选：

```text
LegalProvision.provision_content       → 法条级完整正文知识
ProvisionClause.unit_content           → 条款级完整正文知识
ProvisionTextParagraph.unit_content    → 最小正文单元知识
```

三个层级不是互斥的优先级或兜底关系。只要相应正文有效，均可生成候选知识。法条级知识用于保留完整法条及共同语境，条款级知识用于保留可独立引用的完整条款，最小正文单元知识用于支持精确检索。不同层级之间允许存在语义包含和部分重复，不能因为父级能够由多个子级拼接得到就删除父级知识。

文件级身份、目的和范围知识不参与正文层级比较，因为它们表达的是文件事实，而不是具体条款原文。正文来源层级可以通过既有的来源节点类型和法律定位进行内部识别，不需要向自然语言正文追加层级说明，也不强制新增 `knowledge_level` 字段。

### 7.2 完全重复判定

对父级正文执行保留标点的空白归一化，然后与有序子节点正文比较：

1. 父子正文完全相同：只保留一条，优先保留定位更精确、来源更直接的子级知识。
2. 父级正文由多个子级正文组合而成：父级和子级均保留，分别提供整体上下文和细粒度知识。
3. 父级与子级仅部分重叠：父级和子级均保留，不对法规原文进行截取或改写。
4. 父级没有有效子节点：只要父级原文有效，正常生成对应层级知识。
5. 父级只有摘要而没有原文：不使用摘要替代正文。

完全重复的判断应同时满足：属于同一法规文件、位于同一祖先链或明确对应同一法律位置、标准化后的正文完全一致。文本相似、父级包含子级或多个子级可以拼成父级，均不属于应删除的完全重复。

### 7.3 嵌套正文单元

Schema 允许 `ProvisionTextParagraph` 继续包含更细粒度的 `ProvisionTextParagraph`。如果实际图谱出现该关系，各层有效正文均可生成候选；只有父段与某个子段标准化后完全相同时才保留一条。当前图谱未出现该关系时，不应人为构造嵌套层级。

### 7.4 知识规模与受控重复

按照当前图谱统计，三个正文层级合计可形成最多 35,917 个原始候选，其中包括 3,041 个法条级候选、12,422 个条款级候选和 20,454 个最小正文单元候选。该数量是进入内容校验和完全重复去重之前的理论上限，不等同于最终知识条目数。

最终数量只应因正文为空、语言异常、来源无法定位、内容不具备法规语义或父子正文完全相同而减少。父级与子级表达相近、父级包含子级、多个子级共同组成父级等情况属于为不同检索粒度服务的受控重复，应予保留。转换统计应分别报告三个层级的候选数、有效产出数和完全重复删除数，避免因总量统计掩盖某一层级被过度过滤的问题。

## 8. 特殊信息处理

### 8.1 量化信息处理

`quantitative_indicator` 在 Neo4j 中通常保存为 JSON 字符串，转化时解析为结构化对象。有效对象示例：

```json
{
  "raw_text": "at least one",
  "value_type": "count",
  "min": 1,
  "max": null,
  "unit": "",
  "relation": "lower_bound"
}
```

处理要求：

1. 量化对象非空时，`quantitative_feature` 应为 `Quantitative`。
2. `raw_text` 应能在来源正文中核验，或与正文表达一致。
3. `value_type`、数值边界、单位和关系应符合 Schema 允许结构。
4. 量化信息不形成独立知识类型。正文仍按 `legal_provision` 及其来源层级规则输出，结构化量化对象只放入元数据。
5. 不再生成“The minimum count is 1.”之类脱离原文条件的第二条知识。
6. 对象解析失败或联动不一致时，仍可把有效原文作为普通 `legal_provision` 输出，但移除或标记无效量化元数据并记录问题；异常处理本身不生成自然语言知识。

### 8.2 修订法规知识

当原文及 `is_amendment_article`、`amendment_action`、`amendment_target` 表明条文执行修订、插入、替换、删除或废止时，知识类型使用 `amendment_provision`。

修订知识必须保留完整原文，因为生效日期、过渡条款、例外和保留义务可能位于同一句中。`amendment_action` 和 `amendment_target` 仅作元数据，不单独拼成简化句。

### 8.3 条件、后果与例外

正文中的条件、法律后果和例外不得被拆成互相脱离的多条知识。若完整 `unit_content` 已表达这些语义，输出完整原文一条，并把对应结构化字段放入元数据。只有未来存在明确证据范围和独立完整文本时，才可考虑拆分。

### 8.4 立法理由、编辑说明与修订沿革

立法理由、Editorial Notes、Amendments history、Statutory Notes 和其他说明性区块不因出现在原始文件中就自动成为规范知识。只有抽取流程已经将其识别为合法业务实体，并且正文类型、来源和语义均通过校验时，才可按相应实体规则处理。目录、孤立标题和页码始终过滤。

## 9. 英文输出规则

### 9.1 正文语言

以下内容必须使用英文：

1. `content` 知识正文。
2. `knowledge_type` 受控值。
3. 模板中的连接词和状态说明。
4. TXT 文件中的全部知识条目。

法规官方名称、简称、条文编号和引用文本按原文保留。风险类型等系统受控分类即使为中文，也只能出现在 JSON 元数据中，不能插入 `content`。

### 9.2 异常语言处理

来源正文若异常混入中文说明，应执行以下处理：

1. 不自动翻译为英文。
2. 不与英文原文拼接。
3. 将候选标记为语言异常并进入复核。
4. 其他正常英文正文继续转化，不因单个异常节点阻断整份文件。

### 9.3 原文保持

转化仅允许进行以下轻量处理：

1. 去除 Markdown 标题符号和已知页眉页脚噪声。
2. 合并非语义性的连续空白。
3. 保留原始标点、数字、货币符号、百分号、条文编号和法律引用。
4. 不替换法律情态词，不改写长句，不纠正可能影响法律含义的原文表达。

## 10. 属性白名单、去重与校验

### 10.1 Schema 驱动的属性白名单

允许参与知识生成或元数据保留的业务属性应从 `en_law_v1`、`en_law_v2` 和 `en_law_v3` Schema 中提取，并补充少量来源恢复所需的固定基础字段。对于 Schema 外动态属性：

1. 不作为知识正文来源。
2. 不进入公开元数据。
3. 记录字段名、节点类型和出现次数。
4. 不因未知字段存在而丢弃节点的合法原文。

Neo4j 的 `identity`、`elementId`、`labels`，以及 `graph_tag`、`graph_level` 等字段只用于图谱解析或审计，不参与正文组装。

### 10.2 去重键

知识去重不能依赖节点名称。建议使用：

```text
document identity
  + knowledge type family
  + resolved source path
  + normalized source content
```

其中 `knowledge type family` 用于区分文件事实、规范正文、制定依据和引用知识。跨层比较只用于删除同一法规、同一法律位置或同一祖先链中正文完全相同的机械重复；不得因为父级包含子级、父级由多个子级组合而成或文本高度相似就合并知识。

### 10.3 不应合并的情况

以下知识即使文本相似也不得合并：

1. 位于不同法规文件中的相同正文。
2. 位于不同条文位置且适用上下文不同的相同表述。
3. 相同数值但主体、条件、日期或法律后果不同的规范。
4. 文件级制定依据与正文级引用指向同一法律工具的情况。
5. 一般规范正文与具有明确修订语义的正文。

### 10.4 最低完整性校验

| 知识类型 | 最低完整性要求 |
| --- | --- |
| `document_identity` | 有效文件名称，并至少存在编号、类型或发布主体之一 |
| `document_effect` | 文件名称及至少一个明确日期事实 |
| `document_subject_purpose` | 文件名称及主题或目的之一 |
| `document_scope` | 文件名称及明确适用范围 |
| `legal_provision` | 文件上下文、法律定位和有意义的英文原文 |
| `amendment_provision` | 完整修订原文，以及明确修订行为或目标证据 |
| `legal_basis` | 有效来源文件、`BASED_ON` 关系和非空依据目标 |
| `citation` | 有效来源正文、`CITES` 关系、明确解析的外部引用目标和非空引用文本 |

校验失败的候选不应被强行组装为高置信知识。节点和关系仍可保留在原图谱中，并记录未转化原因。

TXT 文件每行只保存一条英文 `content`。JSON 或 JSONL 建议保存：

```json
  "related_edge_ids": [],

```

字段说明：

| 字段 | 说明 |
| --- | --- |

## 12. 已确定的核心决策

1. **知识正文必须是英文。** 中文受控分类只能放入元数据。
2. **结构字段不重复造句。** 主体、行为、条件和量化字段作为元数据，不再脱离法规原文拼装第二条规则句。
3. **多层正文均可产出。** 法条、条款和最小正文单元分别保留整体语境、完整条款和细粒度内容，允许跨层语义重叠。
4. **只删除正文完全相同的机械重复。** 父级包含子级或多个子级可以组成父级时，不删除父级完整正文。
5. **摘要不替代正文。** `core_topic` 和 `clause_summary` 只服务检索。
6. **组织关系不是知识。** `CONTAINS` 只恢复上下文和层级关系。
7. **制定依据必须有关系。** `LegalBasis` 只通过有效 `BASED_ON` 关系产出。
8. **引用必须可核验。** `Citation` 只通过有效 `CITES` 关系产出。
9. **未解析引用不得臆造目标。** 仅保留原始引用文本和解析状态。
10. **内部或未解析引用不单独输出。** 相关文本随法规正文保留，引用节点信息只用于结构化记录和后续关联。
11. **量化信息不单独输出。** 量化值及校验状态作为元数据，正文仍按一般法规正文知识生成。
12. **修订条文保留完整原文。** 修订动作和目标只作分类与检索字段。
13. **Schema 控制允许属性。** 动态字段不转为知识，但不影响合法原文输出。
14. **格式差异只影响定位和解析。** 三种格式共用统一知识生成规则并保留原始编号，格式本身不形成知识。
15. **格式三暂按原文和 Schema 设计。** 在图谱样本可用后进行同口径实证校验。

## 13. 转化规则汇总与英文示例

本节将转化规则明确分为两类：第一类规则在满足条件时会生成一条最终英文自然语言知识，并计入知识条目数量；第二类规则只负责类型识别、上下文恢复、元数据保留、过滤、去重、语言校验或来源审计，不会单独生成知识正文，也不独立增加知识条目数量。

下表中的知识正文示例全部使用英文。格式一和格式二示例依据当前原始材料、Schema 和 Neo4j 图谱；格式三示例依据现有原始材料和 Schema，用于说明预期规则，尚不表示当前 Neo4j 导出已经覆盖该格式。正式转换时应保留通过校验的完整原文，不能因下表示例篇幅而截断正文。

### 13.1 最终生成自然语言知识的规则

下列规则满足生成条件后，会向最终结果新增一条英文自然语言知识。若同一知识同时满足去重、语言或来源校验规则，还需通过第 13.2 节的非生成规则后才能正式保留。

| # | 知识生成规则 | 生成条件与处理方式 | 最终英文自然语言知识示例 |
| ---: | --- | --- | --- |
| G1 | 文件身份知识 | 文件名称有效，且编号、类型或发布主体至少一个非空；同类字段合并为一条知识 | `Regulation (EU) 2023/956 is a Regulation issued by the European Parliament and the Council.` |
| G2 | 文件发布与效力知识 | 发布日期或生效日期至少一个非空；不推算原始数据中缺失的日期 | `Regulation (EU) 2023/956 was adopted on 10 May 2023 and takes effect on the day following its publication in the Official Journal of the European Union.` |
| G3 | 文件主题与目的知识 | 主题或目的至少一个非空；语义重复的内容只保留一次 | `Regulation (EU) 2023/956 establishes a carbon border adjustment mechanism and aims to prevent carbon leakage and reduce global carbon emissions.` |
| G4 | 文件适用范围知识 | 适用范围明确且能够脱离其他字段独立表达 | `The CLOUD Act applies to foreign-government access to electronic data stored in the United States.` |
| G5 | 制定依据知识 | 存在通过类型和关系校验的制定依据关系，且依据内容明确 | `Regulation (EU) 2023/956 is based on Article 192(1) of the Treaty on the Functioning of the European Union.` |
| G6 | 最小正文单元知识 | 最小正文单元原文有效时生成，补充所属文件和条文定位，不摘要或改写原文；可以与上级完整正文同时存在 | `Under Regulation (EU) 2023/956, Article 1(1) provides: This Regulation establishes a carbon border adjustment mechanism (the 'CBAM') to address greenhouse gas emissions embedded in the goods listed in Annex I on their importation into the customs territory of the Union in order to prevent the risk of carbon leakage, thereby reducing global carbon emissions and supporting the goals of the Paris Agreement, also by creating incentives for the reduction of emissions by operators in third countries.` |
| G7 | 条款级完整正文知识 | `ProvisionClause.unit_content` 有效时生成，不以是否存在正文子节点作为产出前提；仅当其与某个子级正文完全相同时去重 | `Under Regulation (EU) 2023/1115, Article 2 provides: For the purposes of this Regulation, the following definitions apply: (1) ‘relevant commodities’ means cattle, cocoa, coffee, oil palm, rubber, soya and wood; ...` 正式输出保留完整条款。即使条款下还拆有多个正文单元，只要完整条款并非某一个子级正文的完全重复，仍保留该条知识。 |
| G8 | 法条级完整正文知识 | `LegalProvision.provision_content` 有效时生成，不以是否存在条款后代作为产出前提；仅当其与某个后代正文完全相同时去重 | `Under the CLOUD Act, SEC. 101 provides: This division may be cited as the “Clarifying Lawful Overseas Use of Data Act” or the “CLOUD Act”.` 对包含多个条款的法条，法条级完整正文与条款级、最小正文单元知识可以同时保留。正文为空的法条仍不生成知识。 |
| G9 | 修订法规知识 | 原文明示修订、插入、替换、删除或废止；保留完整原文，并将修订信息作为元数据 | `Under Directive 2014/30/EU, Article 45 provides: Directive 2004/108/EC is repealed with effect from 20 April 2016, without prejudice to the obligations of the Member States relating to the time-limit for transposition into national law and the dates of application of the Directive set out in Annex V.` |
| G10 | 外部引用知识 | 来源正文、已明确解析的外部引用目标和引用关系均有效，并能确定引用语义 | `Under Regulation (EU) 2023/956, Article 1(2) cites Directive 2003/87/EC in explaining how the CBAM complements the EU emissions trading system.` |

### 13.2 不单独生成自然语言知识的规则

下列规则参与知识转换过程，但其本身不创建新的英文正文。它们只决定候选知识如何识别、定位、保留、过滤或合并，因此不得被实现为独立的自然语言模板，也不得独立计入知识条目数量。

| # | 非知识生成规则 | 处理方式 | 不生成示例或对最终知识的影响 |
| ---: | --- | --- | --- |
| N1 | 业务类型解析 | 从节点属性读取业务类型，并通过 Neo4j 身份标识解析关系端点；图谱批次标签不作为业务类型 | 识别出 `ProvisionTextParagraph` 后交由 G6 生成正文，但不生成 `This node is a ProvisionTextParagraph.` |
| N2 | 三种格式定位与正文适配 | 使用统一语义模型和 G6 至 G8 处理三种格式，同时保留 `Article`、`SEC.`、`§` 等原始编号；格式三不设置独立知识生成规则 | 格式一保留 `Article 1(1)`、格式二保留 `SEC. 101(a)`、格式三保留 `§ 3729(a)(1)`。格式三正文仍由法条级、条款级或最小正文单元规则生成，格式及编号本身不单独形成知识。 |
| N3 | 规范功能元数据保留 | `mandatory`、`prohibition`、`optional` 用于分类和检索，不额外生成分类句 | Article 43 的正文按 G6 输出，同时记录 `legal_function=prohibition`；不生成 `Article 43 is a prohibition.` |
| N4 | 主体、行为和条件元数据保留 | 完整法规正文已经输出时，不再根据拆分后的主体、行为和条件拼接第二条知识 | 正文可保留为 `Under Directive 2014/30/EU, Article 40(1) provides: ...`，主体、条件和行为仅进入元数据。 |
| N5 | 组织关系过滤 | 包含关系只用于恢复文件、法条和条款上下文，不转换为关系句 | 输出 Article 1 的正文知识后，不生成 `Regulation (EU) 2023/956 contains Article 1.` |
| N6 | 跨层完全重复去重 | 同一法规、同一法律位置或同一祖先链中的父子正文标准化后完全相同时，只保留定位更精确的一条；父级包含多个子级或与子级部分重叠时均保留 | 当条款正文与某一个正文子节点完全相同时，只保留一条 `Under Regulation (EU) 2023/956, Article 1(1) provides: ...`；如果完整条款包含多个子级正文，则条款级和子级知识同时产出。 |
| N7 | Schema 外动态属性过滤 | 未在 Schema 或来源基础白名单中的字段不参与正文生成，只记录校验问题 | 历史字段 `within_45_days_of_receipt` 不单独生成 `The filing must occur within 45 days of receipt.`；合法正文仍可由 G6 至 G8 输出。 |
| N8 | 英文正文约束 | 自然语言模板和知识正文统一使用英文；中文分类值仅作为元数据 | 正文可使用 `The CLOUD Act applies to ...`；`企业国际化经营合规风险` 只保存在 `risk_types` 中，不写入正文。 |
| N9 | 异常语言隔离 | 英文来源异常混入中文说明时，不翻译、不拼接，并将候选内容送入复核 | 不输出 `Under ... provides: 本条规定...` 这类混合语言知识；其他正常英文候选不受影响。 |
| N10 | 同名节点身份解析 | 通过节点身份、父级路径和来源正文区分同名节点，不按名称直接合并 | 两个名称均为 `Article 1(1)` 但属于不同文件时，分别交由正文生成规则处理；本规则本身不生成知识。 |
| N11 | 分类字段元数据保留 | 合规域、经济行业、适用行业和风险类型只用于检索、筛选和关联 | `economic_industries=["General"]` 不生成 `The economic industry of Article 1 is General.` |
| N12 | 格式三说明区块过滤 | Editorial Notes、修订沿革等说明区块不能仅因版式位置成为规范知识，须先满足合法业务实体和语义要求 | `1996—Subsec. (a) ...` 不直接输出为现行义务知识；通过校验的现行条文仍可按 G6 至 G8 输出。 |
| N13 | 来源和审计信息保留 | TXT 只保存最终英文正文；JSON 或 JSONL 保留文件、节点、关系和位置等审计信息 | Article 1(1) 的正文写入 TXT，来源文件、条文位置和节点身份保存在结构化结果中；不生成 `The source file is CBAM Regulation.md.` |
| N14 | 量化信息元数据处理 | 量化对象通过校验时，仅附加到相应法规正文知识的结构化元数据中，不改变知识正文，也不生成独立量化知识 | `at least one auxiliary burner` 随 G6、G7 或 G8 的完整正文输出；`value_type=count`、`min=1` 等只进入元数据，不生成 `The minimum count is 1.` |
| N15 | 无效量化对象处理 | 量化对象无法解析或与量化特征冲突时，移除或标记异常元数据并记录校验问题；有效法规原文仍按 G6 至 G8 处理 | 量化对象损坏时不生成“降级知识”。原文有效则照常输出，异常只进入校验记录。 |
| N16 | 内部或未解析引用过滤 | 内部引用和未解析引用不生成独立引用知识；引用原文随法规正文保留，引用文本和解析状态可用于后续关联 | `Under the CLOUD Act, SEC. 102 cites ...` 不作为独立引用知识生成；SEC. 102 的完整法规正文仍按 G6 至 G8 输出，结构化结果可保留 `resolution_status=unresolved_internal_reference`。 |

### 13.3 生成判定原则

转换器应先应用业务类型识别、定位恢复和 Schema 校验等非生成规则，再判断候选对象是否满足知识生成条件。满足 G1 至 G10 中任一规则并通过语言及来源校验后，可以向最终结果追加一条英文自然语言知识。G6、G7 和 G8 分别从最小正文单元、条款和法条生成候选，三者允许同时产出；只有正文完全相同的跨层候选才按 N6 去重。只满足 N1 至 N16 的对象不得生成知识正文。量化信息、内部或未解析引用、格式适配、组织关系、分类字段和来源信息可以随已生成的知识保存或参与处理，但不能仅凭这些信息新增知识条目。

## 14. 后续实现建议

1. 英文法规转换器应独立于中文法规和国家标准转换逻辑，复用通用 Neo4j 解析和输出组件。
2. 节点索引、关系邻接表和反向来源路径应在转换开始时一次构建，避免对大规模图谱反复全量扫描。
3. 属性白名单应由三套 Schema 自动提取并合并，固定来源字段使用小范围显式补充。
4. 跨层完全重复去重、英文检测、关系端点校验和量化对象解析应默认开启；跨层去重不得扩展为包含关系去重或相似文本去重。
5. 格式三图谱数据导出后，应使用同一规则执行专项验证，重点检查 `§` 多层编号、编辑说明边界、修订沿革和内部引用。
6. 正式转换前应分别输出法条级、条款级和最小正文单元候选数，并统计过滤数、完全重复数、语言异常数、量化异常数和未解析引用数，便于审查转换效果和知识覆盖情况。
