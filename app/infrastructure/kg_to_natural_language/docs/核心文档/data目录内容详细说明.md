# `kg_to_natural_language/data` 目录内容详细说明

本文档介绍 `app/infrastructure/kg_to_natural_language/data` 目录中的正式知识成果，包括目录结构、文件内容、数据格式、统计口径、生成流程、完整性判断和使用注意事项。

本文中的固定结构说明依据当前代码。风险指标知识及其统计均为可持续更新成果，实际数量会随阶段一和全量处理进度变化。

## 第一章 目录定位与结构

### 1.1 目录定位

`data` 是 `kg_to_natural_language` 模块的正式成果目录。它与 `temp` 的区别是：

- `temp` 保存图谱导出、中间转换、逐条元数据和评分检查点；
- `data` 保存经过转换或排序后，可供检索、问答增强和后续系统读取的发布结果。

该目录不保存源 Neo4j 图谱，不保存完整节点关系，也不保存原始法规、标准或案例文件。

### 1.2 当前目录结构

```text
data/
├── type/
│   ├── 法律法规条款.txt
│   ├── 国家标准.txt
│   ├── 行政监管规则.txt
│   ├── 英文法规.txt
│   ├── 合规指引.txt
│   └── 知识条目统计.json
└── risk/
    ├── 处理汇总.json
    └── <三级指标序号>/
        └── all.txt
└── stats/
    └── 知识条目数统计.json
```

### 1.3 三类正式成果的区别

| 比较项 | `data/type` | `data/risk` | `data/stats` |
| --- | --- | --- | --- |
| 组织方式 | 按知识图谱类别组织 | 按三级风险指标组织 | 按风险指标层级组织统计 |
| 数据来源 | 对应类别标签下的全部图谱数据 | 指标映射文件对应的图谱子集 | 指标树和阶段一 `all.json` |
| 主要内容 | 分类知识正文 | 评分排序后的指标知识正文 | 知识数、文件数、覆盖率和诊断 |
| 是否调用大模型 | 否 | 评分阶段调用 | 否 |
| 文件格式 | TXT 和统计 JSON | TXT 和处理汇总 JSON | JSON |

## 第二章 `data/type` 分类知识成果

### 2.1 目录作用

`data/type` 保存五类固定 Neo4j 图谱的分类知识。该目录由包级接口 `process_graphs_by_type()` 生成。

处理流程为：

1. 分别读取“法律法规条款、国家标准、行政监管规则、英文法规、合规指引”五个 Neo4j 标签。
2. 为每类图谱选择对应转换器。
3. 将节点和关系转换为自然语言知识。
4. 校验转换器统计数量与 TXT 非空行数一致。
5. 五类全部处理成功后统一发布五个 TXT 和一个统计 JSON。

批处理采用暂存和备份机制。在五类全部通过校验之前，不会用不完整的新结果替换现有正式成果。

### 2.2 TXT 通用格式

五个分类 TXT 均采用 UTF-8 编码，基本格式为：

```text
第一条自然语言知识
第二条自然语言知识
第三条自然语言知识
```

文件不包含表头、序号、JSON 包装或 Markdown 列表符号。一条物理非空行对应一条知识，读取时可以逐行处理。

知识正文可能较长，尤其是英文法条或完整规范段落。不能根据字符长度把一条长知识拆成多条，否则会破坏原有知识边界。

### 2.3 分类文件说明

五个 TXT 分别保存法律法规条款、国家标准、行政监管规则、英文法规和合规指引知识。分类边界与 Neo4j 固定标签一致；中文类别输出中文知识，英文法规输出英文知识。各文件的具体转换规则由对应专用转换器负责，本目录只保存转换后的正式知识正文。

### 2.4 `知识条目统计.json`

该文件是五类正式成果的批次级统计，结构如下：

```json
{
  "generated_at": "生成时间",
  "status": "success",
  "categories": {
    "类别名称": {
      "label": "Neo4j标签",
      "node_count": 0,
      "relationship_count": 0,
      "knowledge_entry_count": 0,
      "source_file_count": 0,
      "output_file": "类别文件名.txt",
      "status": "success"
    }
  },
  "total_knowledge_entry_count": 0
}
```

字段含义如下：

| 字段 | 含义 |
| --- | --- |
| `generated_at` | 本批五类成果完成发布的时间 |
| `status` | 批处理总体状态；正式发布成功时为 `success` |
| `categories` | 各类别统计对象 |
| `label` | Neo4j 中查询的固定类别标签 |
| `node_count` | 该标签导出的节点数量 |
| `relationship_count` | 起止节点均属于该标签的关系数量 |
| `knowledge_entry_count` | 对应 TXT 的非空知识条目数 |
| `source_file_count` | 转换器识别到的来源文件数 |
| `output_file` | 正式 TXT 文件名 |
| `total_knowledge_entry_count` | 五类知识条目数之和 |

该统计只保存正式发布层面的汇总，不保存每条知识的来源节点和转换器跳过原因。国家标准、英文法规和合规指引的逐条元数据及详细转换统计位于 `temp/jsonl` 和 `temp/csv`，不会随五类批处理复制到 `data/type`。

## 第三章 `data/risk` 风险指标知识成果

### 3.1 目录作用

`data/risk` 按三级风险指标保存最终知识。每个指标目录中的 `all.txt` 不是某一个文件的知识，而是该三级指标所有已命中映射文件知识的汇总。

映射文件可能来自以下五类图谱：

- 法律法规条款；
- 国家标准；
- 行政监管规则；
- 英文法规；
- 合规指引。

因此，一个风险指标 `all.txt` 可能同时包含多份文件、多个图谱类别以及中英文知识。

### 3.2 指标目录命名

目录名称使用三级指标的四段序号，例如：

```text
1.1.1.1
2.3.1.1
6.x.x.x
```

第一段数字对应六类风险根节点，后续数字表示指标层级路径。具体指标名称、描述和风险类型不写在目录名中，而保存在阶段一 `temp/risk/<指标>/all.json` 以及全量处理汇总中。

### 3.3 `all.txt` 的内容来源

生成一个指标 `all.txt` 时，系统执行以下过程：

1. 从风险映射树读取指标名称、指标描述和映射文件。
2. 只选取映射树中“已找到”非空的文件。
3. 在五类 Neo4j 标签中按文件名查找对应文件子图。
4. 使用相应类别转换器生成自然语言知识。
5. 汇总所有命中文件的知识。
6. 将每条知识与指标描述提交给模型计算关联度和原因。
7. 按评分结果排序并写入 `all.txt`。

所以该文件表达的是“该指标映射文件中可获得的知识集合”，并不是大模型重新生成的指标解释。大模型只负责关联度评分和排序，不改写知识正文。

### 3.4 `all.txt` 的格式

`all.txt` 使用 UTF-8 编码，每行一条知识，不包含表头、分数、评分原因、来源文件字段或 JSON 包装。

```text
关联度最高的知识条目
关联度次高的知识条目
……
```

正式 TXT 只保留知识正文，是为了直接供检索和模型输入使用。若需要查看每条知识的来源文件、图谱类别、映射来源、关联度和原因，应读取：

```text
temp/risk/<三级指标序号>/all.json
```

### 3.5 排序规则

风险知识排序规则为：

1. 评分成功的知识排在评分失败的知识之前。
2. 评分成功知识按关联度从高到低排列。
3. 关联度相同时，中文知识优先。
4. 语言也相同时，按原始生成顺序和稳定知识编号排序。
5. 评分失败知识仍保留在 `all.txt` 末尾，不因评分失败而删除。

因此，文件前部通常是与指标最直接相关的知识，文件后部可能包含低关联知识或评分失败但仍保留的知识。

### 3.6 去重范围

阶段一会对同一图谱类别、同一规范化来源文件中的重复知识进行合并，并合并其映射来源。

知识编号包含图谱类别、来源文件键和知识正文。因此，两个不同来源文件即使产生完全相同的正文，也可能保留为两条记录。转换器层还会执行各自的语义去重，但不会承诺消除所有跨文件重复。

同一知识也可能出现在多个三级指标目录中，因为每个指标独立根据自己的映射文件生成知识。这种跨指标重复反映多个指标共享同一法规、标准或指引依据，不应简单视为生成错误。

### 3.7 最终成果完成判定

全量处理默认以以下条件判断一个指标已经有最终成果：

```text
data/risk/<三级指标序号>/all.txt 存在，且至少包含一条非空知识。
```

仅存在指标目录不能算完成；空 `all.txt` 也不能算完成。若最终成果无效，即使 `temp/risk/<指标>` 已有阶段一数据，全量处理仍会重跑该指标。

需要注意：当前断点续跑只依据最终 TXT 是否非空，不依据上一次评分是否全部成功。一个存在非空 `all.txt` 的部分成功指标也会被默认跳过。若需要重新评分，应显式调用阶段二或使用强制重跑参数。

## 第四章 `处理汇总.json`

### 4.1 文件作用

`data/risk/处理汇总.json` 是全量三级指标处理的运行级汇总。程序启动后先写入 `running` 状态，之后在跳过已有指标、完成指标或记录失败时持续更新，任务结束后写入最终状态。

该文件既是结果统计，也是长时间运行任务的进度检查点。

### 4.2 顶层结构

```json
{
  "status": "running | success | partial_success | failed",
  "risk_tree_path": "风险树路径",
  "model_name": "评分模型名称",
  "indicator_count": 0,
  "completed_indicator_count": 0,
  "pending_indicator_count": 0,
  "processed_indicator_count": 0,
  "skipped_existing_indicator_count": 0,
  "success_indicator_count": 0,
  "partial_success_indicator_count": 0,
  "failure_indicator_count": 0,
  "knowledge_count": 0,
  "new_knowledge_count": 0,
  "existing_knowledge_count": 0,
  "ranking_success_count": 0,
  "ranking_failure_count": 0,
  "started_at": "开始时间",
  "completed_at": "完成时间或null",
  "elapsed_seconds": 0,
  "temp_output_root": "阶段一根目录",
  "data_output_root": "正式成果根目录",
  "summary_path": "本文件路径",
  "results": [],
  "skipped_existing": [],
  "failures": []
}
```

### 4.3 进度字段

| 字段 | 含义 |
| --- | --- |
| `indicator_count` | 风险树中全部三级指标数 |
| `completed_indicator_count` | 当前运行已经检查过的指标数，包括实际处理和跳过已有 |
| `pending_indicator_count` | 当前运行尚未检查的指标数 |
| `processed_indicator_count` | 当前运行实际调用完整处理流程的指标数，包括成功和失败 |
| `skipped_existing_indicator_count` | 因已有非空最终 `all.txt` 而跳过的指标数 |
| `success_indicator_count` | 当前运行中新处理并全部评分成功的指标数 |
| `partial_success_indicator_count` | 当前运行中新处理但仍有评分失败的指标数 |
| `failure_indicator_count` | 当前运行未形成正常结果的指标数 |

“磁盘中已有多少指标目录”和“当前运行已完成多少指标”不是同一个统计。程序按指标序号逐个检查，尚未遍历到的后续指标即使磁盘中已有 `all.txt`，也暂时不会计入本次汇总的 `skipped_existing_indicator_count`。

这解释了盘点时磁盘已有 42 个非空指标成果，而汇总文件只记录当前运行完成 39 个指标的情况。

### 4.4 知识和评分字段

| 字段 | 含义 |
| --- | --- |
| `knowledge_count` | 本次汇总已覆盖的新旧知识总量 |
| `new_knowledge_count` | 当前运行新处理指标产生的知识量 |
| `existing_knowledge_count` | 当前运行已经扫描并跳过的已有知识量 |
| `ranking_success_count` | 汇总范围内评分成功的知识量 |
| `ranking_failure_count` | 汇总范围内评分失败或结果不合法的知识量 |

由于 `all.txt` 不保存评分状态，完整评分成功数和失败数应从汇总 JSON 或阶段一 `all.json` 获取。

### 4.5 结果数组

`results` 保存当前运行实际处理成功或部分成功的指标，主要字段包括：

- 指标序号、名称和风险类型；
- 唯一映射文件数；
- Neo4j 命中文件数和未命中文件数；
- 知识条目数；
- 评分成功数和失败数；
- 阶段一 `all.json` 路径；
- 最终 `all.txt` 路径；
- 处理耗时。

`skipped_existing` 保存因最终成果已存在而跳过的指标。它记录已有知识数量和可读取到的评分统计，但不会重新查询 Neo4j 或调用模型。

`failures` 保存指标序号、异常类型和异常信息，用于定位没有形成正常结果的指标。

### 4.6 状态解释

| 状态 | 含义 |
| --- | --- |
| `running` | 当前全量任务仍在执行，统计会继续变化 |
| `success` | 所有指标均已处理或复用，且新处理部分没有失败 |
| `partial_success` | 已形成部分或大部分成果，但存在指标失败或评分不完整 |
| `failed` | 本次运行未能形成可接受的整体结果 |

盘点时该文件状态为 `running`，开始时间为 `2026-09-01T09:41:17+08:00`。它不应被当作最终批次统计归档，直至状态变为终态。

## 第五章 `data/stats` 风险指标知识统计

### 5.1 文件作用

`data/stats/知识条目数统计.json` 由 `build_risk_indicator_knowledge_statistics()` 生成，用于回答各三级指标及其上级风险层次当前拥有多少知识条目。该文件是统计成果，不包含知识正文，也不替代 `data/risk` 下的最终检索文本。

统计读取风险指标树定义的全部三级指标，并检查各指标在 `temp/risk` 中的阶段一成果。三级指标按实际唯一知识标识计数；二级、一级和六类风险根节点按后代指标中的规范化来源文件去重，同一文件映射到多个指标时不会在同一父级重复累计。六类风险之间可能复用相同文件和知识，因此统计文件只展示各风险根节点及其下级指标的数量，不设置跨六类风险的知识条目数或文件数总计。

### 5.2 主要结构

统计 JSON 主要包括：

- `summary`：风险层次数量、三级指标覆盖数量、知识总数、文件总数和诊断数量；
- `risk_types`：风险根、一级、二级、三级构成的嵌套统计树；
- `missing_indicators`、`invalid_indicators`：尚无成果或成果无效的三级指标；
- `file_conflicts`：同一文件在不同指标中出现知识集合或图谱类别差异的记录；
- `warnings`：声明数量不一致、兼容知识标识和缺失来源等校验信息。

一级和二级指标名称未包含在当前指标树中，因此统计使用指标序号前缀标识这些层次，不推断或生成名称。父级 `is_complete` 只有在全部后代三级指标成果均可用时才为真；存在缺失、无效或一致性问题时，总体状态为 `partial_success`。

### 5.3 更新方式

统计文件不会随着 `temp/risk` 自动变化。阶段一成果新增、删除或更新后，应再次调用统计函数生成新快照。写入采用同目录临时文件和原子替换，失败时不会留下半写的目标 JSON。

## 第六章 数据完整性与使用方式

### 6.1 分类知识完整性检查

对 `data/type` 建议进行以下检查：

1. 五个分类 TXT 和 `知识条目统计.json` 是否同时存在。
2. 统计状态是否为 `success`。
3. 每个 TXT 的非空行数是否等于对应 `knowledge_entry_count`。
4. 五类知识条目数之和是否等于 `total_knowledge_entry_count`。
5. 文件是否能以 UTF-8 正常读取。

当前成果已经满足上述数量一致性检查。

### 6.2 风险知识完整性检查

对单个指标建议检查：

1. 指标目录是否存在。
2. `all.txt` 是否存在且至少有一条非空知识。
3. `temp/risk/<指标>/all.json` 中指标序号是否与目录一致。
4. `knowledge_count` 是否与 `all.txt` 非空行数一致。
5. `ranking_failure_count` 是否为零；若不为零，应判断是否需要补评。
6. 映射文件未命中数量是否在可接受范围内。

对全量成果还应检查 `处理汇总.json` 是否已经进入终态，以及 `completed_indicator_count` 是否等于 `indicator_count`。

### 6.3 检索使用建议

按知识类别检索时，读取 `data/type` 对应 TXT。按风险指标构建检索库或模型上下文时，读取 `data/risk/<指标>/all.txt`。

推荐采用流式逐行读取，避免一次把大型英文法规文件全部载入内存。读取后应保留原始行边界，不要再以句号、分号或换行片段进行未经验证的二次切分。

### 6.4 来源追溯建议

`data` 下 TXT 是面向使用的轻量结果，不是完整审计数据：

- `data/type` 只保存知识正文；
- `data/risk` 只保存排序后的知识正文；
- 分数、原因、来源节点、映射来源等信息不写入最终 TXT。

需要追溯时，应结合以下中间成果：

```text
temp/jsonl/<类别>.jsonl
temp/risk/<三级指标序号>/all.json
temp/risk/<三级指标序号>/<映射文件>.json
```

### 6.5 更新和覆盖原则

- `data/type` 应通过 `process_graphs_by_type()` 整体更新，不建议手工替换单个分类文件。
- `data/risk` 可以按指标逐个生成，也可以通过全量接口断点续跑。
- 默认全量执行会保留并跳过非空已有 `all.txt`。
- 使用 `force=True` 会忽略已有最终成果并重跑全部指标，应谨慎使用。
- `data/stats` 应通过统计接口重新生成，不建议手工修改层级数量。
- 运行期间不要用编辑器长期占用 `处理汇总.json` 或正在写入的 `all.txt`，以免 Windows 文件替换失败。

## 第七章 与其他目录的关系

### 7.1 与 `temp` 的关系

```text
temp/json                 单图 Neo4j 导出
temp/txt                  单次转换知识
temp/jsonl                逐条转换元数据
temp/csv                  转换统计
temp/risk/<指标>          风险知识阶段一及评分检查点
data/type                 五类正式分类知识
data/risk/<指标>          最终风险排序知识
data/stats                风险层级知识统计
```

`temp` 可用于重建和问题排查，`data` 用于正式消费。清理 `temp` 不会直接删除已有 `data`，但会失去逐条来源、评分原因和阶段一重跑依据。

### 7.2 与 Neo4j 的关系

`data/type` 是五类标签全量图谱的自然语言视图；`data/risk` 是基于风险映射树，从五类图谱中按文件筛选后形成的指标视图。

两者均不是 Neo4j 数据的无损备份。自然语言转换会过滤基础设施字段、无效候选、部分内部引用和不能形成独立知识的资源信息。

### 7.3 与风险映射树的关系

`data/risk` 的目录集合和知识来源由 `risk/tree/risk2file_tree.json` 决定。`data/stats` 同时以该树确定完整统计范围。修改指标描述、映射文件或“已找到”值后，已有风险知识和统计不会自动变化，需要重新执行对应处理。

## 第八章 维护结论

`data/type` 保存按图谱类别发布的正式知识正文及批次统计，使用前应结合其统计 JSON 校验当前批次完整性。

`data/risk` 是按三级指标组织的正式排序知识目录；`data/stats` 是依据指标树和阶段一成果生成的风险层级统计目录。统计中的缺失数量和完整性状态应与全量任务进度结合解读，不能把尚未生成的指标视为零知识指标。
