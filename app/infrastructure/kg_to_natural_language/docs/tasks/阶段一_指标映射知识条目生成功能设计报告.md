# 阶段一：指标映射知识条目生成功能设计报告

## 1. 建设目标

本阶段面向三级合规风险指标，建立“指标序号—映射文件—知识图谱—自然语言知识条目”的处理链路。用户输入一个三级指标序号后，系统从指标文件映射树中取得该指标对应的已找到文件，在五类 Neo4j 图谱中定位这些文件的节点和关系，复用现有知识条目转换规则生成逐文件知识 JSON，并汇总形成该指标的 `all.json`。

本阶段只负责生成待排序的指标知识集合，不调用大模型计算关联度，也不生成最终排序 TXT。阶段二将在本阶段 `all.json` 的基础上补充关联度、原因并完成排序发布。

## 3. 功能边界

### 3.1 本阶段实现内容

1. 根据三级指标序号定位唯一指标。
2. 获取指标描述、六类风险类型和映射来源信息。
3. 仅提取`已找到`非空的文件。
4. 对重复映射文件进行规范化去重，同时保留全部地区和映射名称。
5. 在五类 Neo4j 图谱中查询对应文件的节点和关系。
6. 按文件拆分子图并调用对应知识条目转换器。
7. 为每个图谱文件生成独立 JSON。
8. 汇总全部知识并生成 `all.json`。
9. 输出文件命中、转换、知识数量和异常统计。

### 3.2 本阶段不实现内容

1. 不调用大模型计算知识关联度。
2. 不生成最终关联度排序 TXT。
3. 不修改指标映射树。
4. 不爬取`已找到`为空的文件。
5. 不对未进入 Neo4j 的文件重新执行知识图谱抽取。
6. 不使用模糊相似度将未命中文件强制关联到其他文件。
7. 不修改 Neo4j 节点、关系和标签。
8. 不使用 MySQL、MinIO 或任务数据库。

## 4. 总体处理流程

阶段一处理流程如下：

```text
输入三级指标序号
        │
        ▼
加载并索引 risk2file_tree.json
        │
        ▼
定位指标描述、风险类型和映射文件
        │
        ▼
筛选“已找到”非空文件并规范化去重
        │
        ▼
在五类 Neo4j 标签中批量匹配文件
        │
        ├── 未命中：记录到 unmatched_files
        │
        ▼
按图谱类别和文件拆分节点、关系子图
        │
        ▼
调用对应的现有知识条目转换器
        │
        ▼
生成每个文件的知识 JSON
        │
        ▼
知识去重、统计并生成 all.json
```

## 5. 详细功能设计

### 5.1 指标序号解析

系统首次加载指标树时递归建立指标索引：

```text
指标序号 -> 指标上下文
```

指标上下文包括：

- `indicator_number`：三级指标序号；
- `indicator_name`：三级指标对象键名，即简短指标名称；
- `indicator_description`：叶节点`指标描述`字段，即完整指标语义说明；
- `risk_type`：所属六类风险根名称；
- `mapped_files`：按地区组织的映射文件信息。

指标序号应符合数字点分形式，例如`1.1.1.1`。需要处理以下异常：

| 异常 | 处理方式 |
| --- | --- |
| 序号格式非法 | 拒绝执行，不创建成果目录 |
| 指标树中不存在 | 返回指标不存在错误 |
| 同一序号出现多次 | 返回指标树数据冲突错误 |
| 指标叶节点缺少映射文件 | 返回空映射统计，不访问 Neo4j |

### 5.2 映射文件提取

遍历指标的`映射文件`对象，仅选择`已找到`字段非空的叶节点。每条原始映射记录保留：

```json
{
  "region": "中国",
  "mapped_name": "中华人民共和国公司法",
  "raw_text": "《中华人民共和国公司法》",
  "found_filename": "中华人民共和国公司法.txt"
}
```

同一个文件可能出现在多个地区、多个映射名称或同一指标的不同位置。系统按规范化文件键只查询和转换一次，但将所有原始映射来源保存在文件记录的`mapping_sources`中，避免丢失映射依据。

### 5.3 文件名规范化

规范化只处理确定性的格式差异：

1. 去除目录路径，仅保留文件名；
2. 去除`.txt`、`.md`、`.pdf`、`.doc`、`.docx`、`.json`等常用扩展名；
3. 去除首尾空白并统一连续空白；
4. 英文文件名匹配时忽略大小写；
5. 保留法规名称中的年份、版本、条款号和实质文字。

本阶段不使用编辑距离、向量相似度或大模型判断文件名。无法精确规范化匹配的文件进入`unmatched_files`，防止把不同版本、不同法规或不同标准误连。

### 5.4 Neo4j 查询

Neo4j 连接统一使用项目`.env`中的配置：

```text
NEO4J_URI
NEO4J_USERNAME
NEO4J_PASSWORD
NEO4J_DATABASE
```

为了避免按照“文件数×五类标签”逐次访问数据库，系统对目标指标的文件名集合按标签批量查询。节点的`filename`属性兼容字符串和字符串数组。

查询后按“图谱标签+规范化文件名”拆分子图。每个文件子图包含：

- 该文件对应的全部节点；
- 起止节点均属于该文件的内部关系；
- 图谱标签、原始`filename`及查询诊断信息。

若关系无法归属到同一个文件子图，则不进入转换输入，并记录关系隔离统计。若同一文件跨多个标签命中，则分别转换并报告歧义，不静默选择其中一类。

### 5.5 转换器分发

本阶段不重新实现自然语言转写规则，按照图谱标签复用现有转换器：

| 图谱标签 | 使用转换器 |
| --- | --- |
| 法律法规条款 | 中文法规转换器`convert_json_to_text_v2` |
| 行政监管规则 | 中文法规转换器`convert_json_to_text_v2` |
| 国家标准 | 国家标准转换器`convert_national_standard_json_to_text` |
| 英文法规 | 英文法规转换器`convert_english_law_json_to_text` |
| 合规指引 | 通用转换器`convert_json_to_text` |

每个文件子图临时写为转换器兼容的`node.json`和`edge.json`，转换结束后读取该文件的非空知识条目。国家标准和英文法规转换器已有 JSONL 时，可补充已有来源元数据；所有类型均以转换器 TXT 中的非空知识行为最终知识数量基线。

### 5.6 统一知识记录

由于各转换器输出结构不同，阶段一增加统一适配层，但不修改知识正文。每条知识记录设计为：

```json
{
  "knowledge_id": "rk_7dd0...",
  "knowledge": "在《中华人民共和国公司法》第十五条中，……",
  "source_file": "中华人民共和国公司法.txt",
  "graph_filename": "中华人民共和国公司法.txt",
  "graph_category": "法律法规条款",
  "mapping_sources": [
    {
      "region": "中国",
      "mapped_name": "中华人民共和国公司法",
      "raw_text": "《中华人民共和国公司法》"
    }
  ],
  "relevance_score": null,
  "relevance_reason": null,
  "ranking_status": "pending",
  "ranking_error": null
}
```

字段说明：

| 字段 | 含义 |
| --- | --- |
| `knowledge_id` | 由图谱类别、来源文件和知识正文生成的稳定哈希ID |
| `knowledge` | 现有转换器生成的自然语言知识正文 |
| `source_file` | 指标树中的“已找到”文件名 |
| `graph_filename` | Neo4j节点中实际命中的文件名 |
| `graph_category` | 知识来源的五类图谱标签 |
| `mapping_sources` | 文件在指标树中的地区及映射依据 |
| `relevance_score` | 阶段二填写；阶段一为`null` |
| `relevance_reason` | 阶段二填写；阶段一为`null` |
| `ranking_status` | 阶段一统一为`pending` |
| `ranking_error` | 阶段二失败信息；阶段一为`null` |

知识去重键为“图谱类别+来源文件+知识正文”。相同文件因映射树重复引用而产生的知识只保留一次；不同文件中的相同正文继续保留，因为其法律或标准来源不同。

## 8. 异常处理与日志统计

### 8.1 阻断性错误

以下错误应终止阶段一，且不发布新的`all.json`：

- 指标序号格式错误；
- 指标不存在或重复；
- 指标树 JSON 无法解析；
- Neo4j 无法连接；
- 输出目录不可写；
- 转换器执行异常导致本批成果不完整；
- `all.json`结构校验失败。

### 8.2 非阻断问题

以下问题记录后继续处理：

- 某个“已找到”文件未进入 Neo4j；
- 某个文件图谱节点为空；
- 某个文件没有可输出知识；
- 个别关系无法归入同一文件子图；
- 同一文件跨多个图谱标签命中；
- 指标树中同一文件被重复引用。

## 9. 一致性与成果安全

1. 指标序号必须经过格式校验，禁止通过`..`、斜杠等构造目录穿越路径。
2. 每次运行先写入同级暂存目录，全部文件完成并通过校验后再替换正式指标目录。
3. 若本次运行失败，应保留上一次完整成果。
4. JSON统一使用UTF-8、`ensure_ascii=false`和两空格缩进。
5. 正式发布前校验逐文件知识总数与`all.json`去重前后统计能够对应。
6. 同一个指标同一时刻只允许一个阶段一任务发布，避免并发覆盖。
7. 阶段一不清空其他指标目录，也不影响`data/type`分类知识成果。

## 11. 测试方案

### 11.1 单元测试

1. 正确解析`1.1.1.1`，并分别取得指标名称和正式指标描述。
2. 非法序号、未知序号和重复序号能够被拒绝。
3. 仅选择“已找到”非空文件。
4. 路径、扩展名、空白和英文大小写能够正确规范化。
5. 同一文件多次映射时仅处理一次并保留所有来源。
6. 节点`filename`为字符串或数组时均能匹配。
7. 未匹配文件进入清单但不中断任务。
8. 关系只进入起止节点属于同文件的子图。
9. 五类标签分别路由到正确转换器。
10. 知识正文不被阶段一适配器修改。
11. 重复知识被稳定去重，`knowledge_id`重复运行保持一致。
12. 输出目录无法穿越，原子发布失败时旧成果可恢复。

### 11.2 集成测试

选择一个映射文件数量和知识量较小的真实三级指标执行完整阶段一，检查：

- 指标名称与正式指标描述是否分别正确；
- 文件清单是否完全来自非空“已找到”；
- Neo4j匹配类别是否正确；
- 每个命中文件是否生成一个JSON；
- 逐文件知识是否与现有转换器结果一致；
- `all.json`知识数量与逐文件知识汇总是否一致；
- 未命中文件是否完整记录；
- `relevance_score`和`relevance_reason`是否保持`null`；
- `ranking_status`是否统一为`pending`。

## 12. 验收标准

阶段一满足以下条件时视为实现完成：

1. 输入任意有效三级指标序号能够定位唯一指标，并分别取得正确的指标名称和正式指标描述。
2. 文件选择严格以非空“已找到”值为准。
3. 五类图谱均具有明确、可测试的查询和转换路由。
4. 未进入 Neo4j 的文件不会被错误匹配，也不会阻断已命中文件处理。
5. 每个成功转换文件均生成独立 JSON。
6. 指标目录下生成结构完整、可供阶段二直接读取的`all.json`。
7. `all.json`知识正文与现有转换器输出一致，不产生另一套转写规则。
8. 知识和文件重复可被确定性去重，映射来源不丢失。
9. 运行结果包含文件、图谱、知识和异常统计。
10. 全流程不访问 MySQL、MinIO和任务数据库。
11. 失败运行不会覆盖上一次完整成果。
12. 单元测试、集成测试、Python语法检查和OpenSpec严格校验全部通过。

## 13. 阶段一与阶段二衔接

阶段一输出的`all.json`中，每条知识已经包含稳定ID、来源文件、图谱类别和映射来源，同时预留关联度字段。阶段二只需要读取该文件，使用`indicator.description`和`knowledge_entries[].knowledge`进行一对一模型判断，不需要再次读取指标树、查询Neo4j或重新转换知识。

这种分阶段设计可以分别审查“文件和知识是否正确”与“模型排序是否合理”，也允许在不重复执行图谱转换的情况下调整模型、提示词、并发数和评分规则。
