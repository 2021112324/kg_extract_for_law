# 阶段二：知识关联度评分与排序发布功能设计报告

## 1. 建设目标

阶段二承接阶段一生成的三级指标候选知识集合，对每条知识与指标描述之间的关联程度进行独立判断，将评分结果和判断原因回写到 `all.json`，随后按照关联度从高到低排序，并生成供后续检索与应用使用的自然语言知识文件。

本阶段重点解决以下问题：

1. 同一映射文件可能产生大量知识条目，其中只有部分内容与当前三级指标直接相关，需要通过统一标准进行排序。
2. 评分过程涉及大量独立的大模型请求，需要通过异步并发缩短处理时间，同时控制服务压力。
3. 模型可能出现超时、接口异常、无效 JSON 或评分越界等问题，需要保留原知识并支持失败重试和断点续跑。
4. 评分过程需要保留完整审计信息，但最终 TXT 只应包含自然语言知识正文，不能混入评分、原因和内部元数据。

需要特别说明的是，本阶段计算的是知识条目与三级指标描述之间的**关联度**，不是对法规内容真实性或知识正确性的“置信度”。知识正确性主要由上游图谱抽取、转换规则和质量校验保证。

## 2. 输入与前置条件

### 2.1 输入参数

阶段二的主要输入是三级指标序号，例如：

```text
2.3.1.1
```

系统据此读取：

```text
temp/risk/{三级指标序号}/all.json
```

阶段二不再读取指标映射树、不再查询 Neo4j，也不重新调用知识条目转换器。三级指标名称、指标描述、来源文件和候选知识均以阶段一成果为准。

### 2.2 `all.json` 前置校验

启动评分前应完成以下检查：

1. 文件存在且能够按 UTF-8 正常解析。
2. 阶段一状态为成功，知识数组结构完整。
3. 文件中的三级指标序号与调用参数一致。
4. 指标描述非空，可作为模型评分依据。
5. 每条知识具有稳定的知识 ID 和非空知识正文。
6. 评分相关字段缺失时可以补充，字段类型异常时应阻止评分并报告结构错误。

若前置校验失败，系统应在发起任何模型请求前终止，避免对错误文件评分或把结果写入其他指标目录。

## 3. 功能边界

### 3.1 本阶段实现内容

1. 读取并校验阶段一 `all.json`。
2. 为每条候选知识构造独立的关联度判断请求。
3. 使用共享异步客户端和并发控制执行模型调用。
4. 严格解析并校验模型返回的关联度和原因。
5. 将成功、失败、重试和耗时信息回写到对应知识记录。
6. 在处理过程中定期保存检查点，支持中断后继续执行。
7. 按关联度从高到低稳定排序。
8. 将完整评分结果保存到 `all.json`。
9. 将排序后的知识正文保存到 `data/risk/{指标序号}/all.txt`。
10. 在包入口暴露阶段二函数和端到端编排函数。

### 3.2 本阶段不实现内容

1. 不重新抽取知识图谱或修改 Neo4j 数据。
2. 不重新匹配指标与文件。
3. 不修改知识正文，不让模型概括、改写或合并知识。
4. 不把多条知识合并到一次模型请求中。
5. 不把评分和原因写入最终知识正文。
6. 不访问 MySQL、MinIO或任务数据库。
7. 当前不按阈值删除低关联知识，最终 TXT 保留全部非空候选知识，仅改变排列顺序。

## 4. 总体处理流程

阶段二总体流程如下：

```text
输入三级指标序号
        ↓
定位阶段一 all.json
        ↓
校验指标上下文和知识记录
        ↓
识别待评分、失败待重试和已成功记录
        ↓
为每条待处理知识构造独立请求
        ↓
默认 100 并发调用关联度判断模型
        ↓
解析并校验 relevance_score 和 reason
        ↓
分批回写 all.json 检查点
        ↓
成功项按关联度降序稳定排序
        ↓
失败项保留并置于结果末尾
        ↓
原子更新 all.json
        ↓
生成仅含知识正文的 all.txt
        ↓
输出评分、失败、重试和路径统计
```

## 5. 关联度判断设计

### 5.1 判断输入

每次请求只包含以下两项业务内容：

1. 当前三级指标的正式指标描述。
2. 一条待评分的自然语言知识正文。

指标名称可作为辅助上下文，但正式指标描述是关联度判断的主要依据。来源文件、图谱标签和转换器元数据不应直接拼入提示词，避免无关字段干扰模型判断。

### 5.2 判断任务

模型只负责判断当前知识对指标识别、合规判断或风险解释的支撑程度，不负责判断文件是否有效，也不负责重写知识。评分范围为 `0.00` 至 `1.00`：

| 分数范围 | 判断含义 |
| --- | --- |
| `0.90-1.00` | 直接规定或直接解释指标关注的核心要求 |
| `0.70-0.89` | 与指标高度相关，可明显支撑合规判断 |
| `0.40-0.69` | 存在部分关联，主要提供条件、背景或辅助要求 |
| `0.01-0.39` | 关联较弱，仅存在间接联系 |
| `0.00` | 与指标描述没有实质关联 |

上述区间用于稳定模型口径，不作为删除知识的阈值。

### 5.3 模型输出格式

模型必须只返回 JSON 对象：

```json
{
  "relevance_score": 0.92,
  "reason": "该知识直接规定了该指标关注的合规要求。"
}
```

提示词应明确以下限制：

1. 不输出 Markdown 代码围栏。
2. 不输出额外说明或推理过程。
3. 不改写知识正文。
4. 关联度必须是 `0.00` 至 `1.00` 的数值。
5. 原因应简短、明确，并说明知识与指标的具体联系。

## 6. 模型调用与并发设计

### 6.1 配置管理

评分服务采用 OpenAI 兼容的 `chat/completions` 接口。模型名称、接口地址、API Key、并发数、总时限和重试次数通过阶段二专用配置读取。

API Key 必须仅从环境变量 `RISK_RELEVANCE_MODEL_API_KEY` 获取，不得硬编码在代码、报告、日志或结果文件中。日志只允许记录模型名称、脱敏后的服务地址、并发数和时限。

### 6.2 并发执行

系统使用一个共享异步 HTTP 客户端和 `asyncio.Semaphore` 控制请求数量，默认最大并发数为 100。每个协程只处理一条知识，确保不同知识之间互不干扰。

并发数应允许通过函数参数或环境变量降低，以适配模型服务的实际承载能力。传入零、负数或非法并发值时应直接报错，不能静默退化为无上限并发。

### 6.3 单条任务时限

每条知识从首次请求、失败重试到最终返回的总耗时不得超过 120 秒。该时限覆盖：

1. 建立请求和等待响应的时间。
2. 临时错误后的退避等待时间。
3. 模型返回无效结果后的有限重试时间。

达到总时限后，该知识应标记为评分失败，不得继续占用并发资源。

### 6.4 重试策略

以下问题允许在总时限内有限重试：

1. 网络连接异常。
2. 请求超时。
3. HTTP `429` 限流。
4. HTTP `5xx` 服务端异常。
5. 模型返回空内容或无法解析的 JSON。
6. 返回字段缺失、分数越界或原因为空。

明确的参数错误、认证失败和输入结构错误不应持续重试。重试采用有限次数和短退避策略，避免失败请求集中冲击模型服务。

## 7. 响应解析与结果回写

### 7.1 严格解析

模型响应依次经过以下校验：

1. 清理可能出现的代码围栏和首尾空白。
2. 将响应解析为单个 JSON 对象。
3. 检查 `relevance_score` 和 `reason` 是否存在。
4. 检查分数是否为有效数值，而不是布尔值或任意字符串。
5. 检查分数是否位于 `0.00` 至 `1.00`。
6. 将有效分数规范到两位小数。
7. 检查原因是否为非空文本。

对于超出范围的分数，不能通过截断方式伪造有效结果，应视为无效响应并按规则重试。

### 7.2 成功记录

评分成功后更新对应知识记录：

```json
{
  "knowledge_id": "risk_xxx",
  "knowledge": "原始知识正文",
  "relevance_score": 0.92,
  "relevance_reason": "该知识直接规定了指标关注的合规要求。",
  "ranking_status": "success",
  "ranking_error": null
}
```

知识正文、来源文件、图谱类别和阶段一映射信息保持不变。

### 7.3 失败记录

评分失败时仍保留原知识：

```json
{
  "knowledge_id": "risk_xxx",
  "knowledge": "原始知识正文",
  "relevance_score": null,
  "relevance_reason": null,
  "ranking_status": "failed",
  "ranking_error": "评分请求在规定时限内未获得有效响应"
}
```

错误摘要不得包含 API Key、请求头、完整提示词或其他敏感配置。

## 8. 检查点与断点续跑

评分任务可能包含数百或更多知识条目。为避免程序中断后全部重新执行，系统应按固定完成批次原子更新 `all.json` 检查点。

默认续跑规则如下：

1. `ranking_status=success` 且分数、原因合法的记录直接跳过。
2. `ranking_status=pending` 的记录进入评分队列。
3. `ranking_status=failed` 的记录重新尝试评分。
4. 使用 `force=true` 时，全部知识重新评分。

检查点写入采用“临时文件写入、结构校验、原子替换”的方式，防止进程中断留下无法解析的半成品 JSON。

阶段二完成后，`all.json` 应增加评分汇总信息，包括模型名称、总知识数、评分成功数、评分失败数、跳过数、重试数、开始时间、完成时间和总耗时，但不得保存 API Key。

## 9. 排序规则

排序在评分任务结束后统一执行：

1. 评分成功的知识按照 `relevance_score` 从高到低排列。
2. 分数相同时，中文知识优先于其他语言知识。中文属性根据知识正文是否包含中文汉字判断，不依赖图谱类别。
3. 语言优先级相同时，按照阶段一的 `original_order` 保持稳定顺序。
4. 若原始顺序仍相同，以 `knowledge_id` 作为确定性排序依据。
5. 未获得有效评分的知识统一置于成功项之后。
6. 失败项之间同样按中文优先、原始顺序和知识ID稳定排列，不伪造 `0.00` 分数。

中文优先是同分条件下的次级排序规则，关联度仍是成功知识的首要排序条件，因此不会出现低关联中文知识排在高关联外文知识之前。该规则保证同一份输入在评分结果相同的情况下能够产生稳定、可复现的输出。

## 10. 最终 TXT 设计

最终文件路径为：

```text
data/risk/{三级指标序号}/all.txt
```

TXT 只保存排序后的知识正文，每条知识占一行，例如：

```text
第一条与指标高度相关的知识……
第二条与指标较相关的知识……
第三条提供辅助背景的知识……
```

最终 TXT 不包含以下内容：

1. 关联度分数。
2. 评分原因。
3. 知识 ID。
4. 来源文件和图谱标签。
5. `converter_metadata` 等转换器内部元数据。
6. JSON 字段名、括号或其他结构包装。

完整评分和审计信息只保留在 `temp/risk/{指标序号}/all.json` 中。

按照当前需求，阶段二**只排序、不按分数删除知识**。因此，如果阶段一候选池包含 510 条非空且已去重知识，最终 TXT 原则上仍包含 510 条知识正文，只是高关联知识位于前部，低关联知识位于后部。后续若需要只发布高关联知识，应另行增加阈值或 Top-K 发布规则，不能在当前阶段二中隐式删除。

## 11. 公共函数设计

### 11.1 阶段二函数

```python
async def rank_risk_indicator_knowledge(
    indicator_number: str,
    *,
    max_concurrency: int = 100,
    force: bool = False,
) -> dict:
    ...
```

主要职责：

1. 校验阶段一 `all.json`。
2. 执行并发评分和断点续跑。
3. 更新并排序 `all.json`。
4. 发布最终 `all.txt`。
5. 返回评分数量、失败数量、输出路径和耗时统计。

### 11.2 端到端函数

```python
async def process_risk_indicator_knowledge(
    indicator_number: str,
    *,
    max_concurrency: int = 100,
    force: bool = False,
) -> dict:
    ...
```

该函数依次调用：

1. `generate_risk_indicator_knowledge` 完成阶段一。
2. `rank_risk_indicator_knowledge` 完成阶段二。

两个函数均应在包级 `__init__.py` 和 `__all__` 中公开。阶段二实现完成前不应暴露指向空实现或占位实现的接口。

## 12. 日志与统计

阶段二日志应至少包含：

1. 指标序号、指标名称和知识总数。
2. 待评分、已跳过和失败待重试数量。
3. 模型名称、脱敏接口地址、并发数和单条总时限。
4. 当前完成数、成功数、失败数、重试数和耗时。
5. 超时、限流、服务端异常和响应校验失败统计。
6. 检查点保存状态。
7. `all.json` 和 `all.txt` 的最终路径。

任务结束时应把汇总统计放在日志末尾，避免被大量过程日志淹没。单条失败日志只记录知识 ID 和脱敏错误摘要，不输出完整知识正文和模型请求内容。

## 13. 异常处理

### 13.1 阻断性错误

以下问题应终止整个阶段二任务：

1. 阶段一 `all.json` 不存在或无法解析。
2. 指标序号不一致。
3. 阶段一状态不成功。
4. 指标描述缺失。
5. 知识数组结构不合法。
6. API Key 未配置或模型配置无效。
7. 输出目录不可创建或检查点无法写入。

### 13.2 单条可隔离错误

以下问题只影响当前知识，不应导致其他知识停止评分：

1. 单条请求超时。
2. 单条请求达到最大重试次数。
3. 单条模型响应无法解析。
4. 单条分数或原因校验失败。

单条失败应进入失败统计并保留原始知识，其他协程继续执行。

## 14. 安全与依赖约束

1. 不在源代码中保存 API Key。
2. 不在日志、异常、JSON或TXT中输出 API Key。
3. 不初始化或访问 MySQL、MinIO和任务数据库。
4. 只访问实验室模型服务和本地阶段成果目录。
5. 输出路径必须限制在当前三级指标目录内，并校验指标序号，防止路径穿越。
6. 模型不得修改知识正文，TXT始终使用阶段一原始知识文本。

## 15. 测试方案

### 15.1 单元测试

1. `all.json` 缺失、损坏和指标序号不一致测试。
2. 指标描述为空和知识正文为空测试。
3. 合法 JSON、代码围栏 JSON和额外文本响应解析测试。
4. 分数字符串、布尔值、越界值和空原因测试。
5. 100 并发上限测试，确认最大在途请求不超过配置值。
6. 超时、`429`、`5xx`、网络错误和重试次数测试。
7. 单条失败不影响其他知识测试。
8. 检查点原子写入和中断续跑测试。
9. 默认跳过成功项和 `force` 全量重评测试。
10. 分数降序、同分中文优先、同语言稳定顺序和失败项置后测试。
11. TXT仅包含知识正文测试。
12. 日志和异常不泄露 API Key 测试。

### 15.2 集成测试

1. 使用模拟模型服务对小型 `all.json` 完成完整评分、排序和发布。
2. 人为设置部分超时和无效响应，验证失败隔离与检查点恢复。
3. 使用少量真实知识调用实验室模型，人工检查关联度和原因是否合理。
4. 使用阶段一真实成果验证最终 TXT 行数、顺序和正文一致性。
5. 验证阶段二不会连接 Neo4j、MySQL或MinIO。

真实模型测试应先使用少量知识确认提示词和评分口径，再执行完整指标任务，避免在提示词未经验证时产生大量无效调用。

## 16. 验收标准

阶段二满足以下条件时可视为实现完成：

1. 能够通过三级指标序号读取并校验对应的阶段一成果。
2. 每次模型请求只包含一个指标描述和一条知识。
3. 默认最大并发数为 100，且单条任务总时限不超过 120 秒。
4. 模型结果经过严格 JSON、字段、类型和范围校验。
5. 成功结果包含关联度和原因，失败结果保留原知识且不伪造分数。
6. 支持原子检查点、失败重试和断点续跑。
7. `all.json` 保存完整评分、原因、状态和统计信息。
8. `all.txt` 仅包含按关联度从高到低排列的知识正文。
9. 阶段二不改变知识正文，不访问 MySQL和MinIO。
10. 包入口能够正常导入阶段二函数和端到端函数。
11. 日志末尾能够看到成功、失败、重试、耗时和输出路径汇总。
12. 自动化测试和少量真实模型测试通过，且不存在密钥泄露。

## 17. 与阶段一及后续应用的关系

阶段一负责生成完整、可审计的候选知识集合，阶段二负责衡量候选知识与当前三级指标的关联程度并确定展示顺序。两个阶段通过 `all.json` 解耦：阶段二无需了解图谱查询和转换器细节，阶段一也无需依赖模型评分服务。

最终 `all.txt` 是面向检索和后续应用的简洁成果，只包含自然语言知识；`all.json` 是供续跑、审计和问题定位使用的过程成果。该设计既保留候选知识的完整性，又使高关联知识优先进入下游检索范围。
